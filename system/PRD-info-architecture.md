# PRD — 정보 아키텍처

> **문서 지위**: 이 문서가 spec이자 goal이다. 구현이 이 문서와 어긋나면 그것은 버그다.
> **변경 규율**: 대화 중에 바꾸지 않는다. 정책 변경이 필요하면 **이 문서를 먼저 고치고** §12에 남긴다. 구현부터 바꾸는 것은 금지.
> **버전 규약**: 버전은 **구현된 상태**를 가리킨다. 스펙 초안 단계는 `v0.x`이며, 첫 구현이 §10 검증을 통과할 때 `v1.0`을 부여한다. 계획 수정은 버전을 올리지 않는다.
> **현재 버전**: `v0.1` (초안 — 미구현)
> **위치**: 추적되는(git) 공간. 변경 이력이 곧 보호 장치다. 비추적 공간은 이력이 없어 보호 요건 미달, 실행물 공간은 의미가 흐려진다.
> **용어**: 이 문서에서 **유저**는 워크스페이스 소유자, **에이전트**는 그와 함께 일하는 AI를 가리킨다.

---

## 1. 목적

세션이 끊겨도 정보가 소실·왜곡되지 않게 하고, 자라나는 정보를 유기적으로 관리·분석·종합·확장하면서 유저와 대화로 일하는 것.

정보 저장이 목적이 아니다. **대화의 품질이 목적이고, 저장은 수단이다.**

---

## 2. 문제 정의 — 실패는 두 층에서 일어난다

### 2.1 정보 층 (I) — 기록된 것의 문제

| ID | 실패 |
|---|---|
| **I-1** | **재제안** — 이미 결정된 것을 다시 묻거나 제안한다 |
| **I-2** | **미확인 단언** — 확인 가능한 기록을 조회하지 않고 구체를 사실처럼 말한다 |
| **I-3** | **추론의 사실화** — 근거 없이 추론을 결론으로 승격한다 |
| **I-4** | **문서 동결 오류** — 원점 검증이 불가능한 파생 문서의 오류가 굳어 재생산된다 |
| **I-5** | **폐기 프레임 재발** — 이미 기각된 방향을 다시 제시한다 |

### 2.2 에이전트 층 (A) — 처리 과정의 문제

**전제: 정보가 완전해도 에이전트는 실패한다.** 분류·태깅·리콜·해석·합성은 모두 판단이며, 판단에는 오류율이 있다. 이 층은 **제거 대상이 아니라 감지·회복 설계의 대상**이다.

| ID | 실패 |
|---|---|
| **A-1** | **분류 실패** — 사실/전언/추론/의견의 등급을 잘못 판정 |
| **A-2** | **태깅 실패** — 태그 누락·오류로 이후 검색이 불가능해짐 |
| **A-3** | **리콜 실패** — 기록에 있으나 조회하지 않음. 본질은 *존재를 모르는 것*이므로 **조회 규율만으로 막을 수 없다**(→ §6.4) |
| **A-4** | **해석 실패** — 찾았으나 오독하거나 맥락에 맞지 않게 적용 |
| **A-5** | **합성 실패** — 여러 사실을 묶으며 근거 없는 연결을 만듦 |

### 2.3 두 층의 관계

I 계열은 **저장 규율**로, A 계열은 **행동 규율과 구조**로 다룬다. 전자만 갖추면 "정확한 기록을 조회하지 않는 에이전트"가 된다.

**사례는 이 문서에 적지 않는다** — 구체 사례는 telemetry 기록(§6.6)에 남긴다. 스펙은 추상을, 기록은 구체를 담는다(§4.2와 동일한 분리).

## 3. 성공 판정

측정 가능한 형태로만 정의한다.

1. **신선 세션 테스트** — 새 세션에서 핵심 사실 20문에 **오답 0**. "모른다"는 오답이 아니다.
2. **재제안 0건.**
3. **감사 30초** — 임의의 주장을 30초 안에 원점까지 추적 가능.
4. **정정 비용** — 유저 정정이 한 문장으로 끝나고 같은 오류가 재발하지 않는다.
5. **대화 속도** — 조회·갱신 규율이 일상 대화에 체감 지연을 만들지 않는다.

## 4. 원칙

### 4.1 소스 오브 트루스 = 정보가 처음 생성된 지점

파일 종류로 등급을 매기지 않는다. **그 정보가 처음 존재하게 된 순간의 산물**에 최대한 가까이 간다.

| 정보의 종류 | 원점 | 파생 |
|---|---|---|
| 대면·통화 | 오디오 | 전사 → 판독 → 요약 |
| 메시지(채팅·메일) | 메시지 실물 | 스크린샷·인용 |
| 세션 대화 | 대화 로그 | 요약·문서화 |
| **유저의 결정·선호·계획·정정** | **유저의 발화** | 에이전트가 작성한 모든 문서 |
| 외부 사실 | 1차 출처 | 요약·2차 보도 |

- 등급은 **원점으로부터의 파생 거리**로 정해진다: 원점 > 1차 파생 > 2차 파생 > 에이전트 추론.
- 이 정의로부터 **"유저 발화가 파생 문서를 이긴다"가 규칙이 아니라 귀결로 도출된다** — 유저의 결정은 유저에게서 생성되므로 그의 발화가 원점이다.
- **충돌 규칙**: 파생 기록과 유저의 기억이 어긋나면 **어느 쪽도 조용히 채택하지 않는다.** 출처와 함께 충돌을 드러내고 유저가 판정한다. 인간 기억에도 오류가 있다.

### 4.2 불변 기록과 가변 해석의 분리

- **기록(사실)**: 누가·언제·무엇을·어디서. 추가 전용이며, 수정은 상태 전이(대체됨/철회됨)로만 한다.
- **해석(분석·판단·태그·요약)**: 파생물이며 폐기 가능하다. 오독이 발견되면 해석만 버리고 다시 만든다.
- 목적: 에이전트 실패의 **폭발 반경 제한.** 해석 오류가 기록을 오염시키면 복구가 불가능해진다.
- 이 분리는 **이 문서 자체에도 적용된다**(§2.3).

### 4.3 다중 방어

하나의 완벽한 게이트를 만들지 않는다. 같은 오류를 잡을 기회를 여러 층에 둔다: 저장 시 상태 표시 → 세션 시작 시 핫셋 로드 → 조회 게이트 → 발화 시 등급 표시 → 유저 정정 → 사후 감사.

### 4.4 열화 모드

기록이 없거나·낡았거나·모순될 때의 기본 동작은 **"모른다"**이다. 추측으로 메우지 않는다. 모른다고 말하는 것은 실패가 아니라 정상 동작이다.

### 4.5 유지비용

**유저의 유지 부담 ≈ 0.** 에이전트가 쓰고 갱신하며, 유저는 정정만 한다. 유저의 정기 입력을 요구하는 설계는 실패한 설계다.

## 5. 범위

| 층 | 범위 | 근거 |
|---|---|---|
| **규칙** (출처 등급 · 조회 게이트 · 선행 질의 · 불변/파생 분리 · 열화 모드) | **워크스페이스의 모든 정보**, 전 도메인, 첫날부터 | 실패 모드가 도메인 무관하다. 최종 목적이 도메인을 가로지르는 통찰 생성이므로, 규칙이 한 도메인에만 있으면 교차 탐색이 성립하지 않는다 |
| **기록의 적극 추출** | **수요 주도** — *휘발성 × 결정 하중*이 높은 영역부터 | 전량 추출은 과잉설계다. 안정된 문서는 이미 문서로 충분하며, 기록의 가치는 그 곱에 비례한다 |

**비적용**: 프로젝트 지시가 동결로 규정한 영역(제출 증빙·완결 기록·연구 원료·동결 산출물). 참조 대상이지 갱신 대상이 아니다.

## 6. 요건

> 이 절은 **무엇이 필요한가**를 정한다. **어떻게 만들지는 정하지 않는다** — 대안을 비교해 결정하고 §11에 남긴다.

### 6.1 사실 기록

- 원자 단위: **한 레코드 = 한 사실.**
- 필수 필드: 내용 · **출처(원점과 파생 경로, 위치)** · 발화자 · 날짜 · **상태** · 주제 태그 · 대체/철회 관계.
- 상태: `확정` · `전언` · `추론` · `미해결` · **`결정됨(재제안 금지)`** · `대체됨` · `철회됨`.
- **`결정됨`은 I-1을 직접 막는 상태**다. 이 상태 항목의 재제안은 버그다.
- **`철회됨`을 삭제하지 않는다** — 폐기 기록이 I-5를 막는다.

### 6.2 조회

- 키워드·주제·상태·인물·기간으로 조회 가능.
- **태그에만 의존하지 않는다**(A-2 대비) — 전문 검색 경로를 항상 확보한다.
- **감사 사슬 출력**: 사실 → 파생 문서 → 전사 위치 → 원점 파일을 한 번에.

### 6.3 조회 게이트 — 티어링

모든 발화에 조회를 걸지 않는다. 그러면 대화가 느려지고 시스템이 버려진다.

| 티어 | 행위 | 조회 |
|---|---|---|
| **T0** | 잡담 · 설명 · 요약 · 개념 해설 · 정서적 대응 | 불필요 |
| **T1** | **사실 단언** | 필수 |
| **T2** | **행동 제안 · 요구 목록 · 전략 권고** | 필수 + **`결정됨` 확인** |
| **T3** | 문서 작성·갱신 | 필수 + 충돌 검사 |

### 6.4 핫/콜드 2단

A-3의 본질은 *존재를 모르는 것*이므로 조회 규율만으로 막을 수 없다.

- **핫셋** — 세션 시작 시 **자동 로드**. 소규모 유지(상한 필요). 내용은 `결정됨` · `철회됨` · 현재 국면의 하중 큰 사실 · 미해결 질문. 즉 **위반 위험이 가장 큰 부분집합.**
- **콜드셋** — 전체 코퍼스. 필요 시 조회.
- 핫셋이 커지면 로드 비용과 주의 분산이 생기므로 **상한을 두고 국면 종료 시 콜드로 강등**한다.

### 6.5 갱신 시점과 비용 — 트리거로 쓰고, 스캔하지 않는다

> **비용은 쓰기가 아니라 스캔에 있다.** 대부분의 대화 턴은 기록할 것이 없다. 매 턴 스캔은 대부분이 낭비이고, 매 턴 백그라운드 실행은 오버헤드가 정보 생성률을 초과한다.

| 방식 | 언제 | 비용 |
|---|---|---|
| **인라인 즉시 추가** (기본) | 트리거 발생 시: ①유저 정정 ②원점 소스의 새 사실 ③결정 발생 ④상태 전이 | 쓰기 1회 |
| **배치 통합** (드물게, 명시적) | 대량 원료 유입 후, 국면 종료 후 | 1회성 |
| **비동기 실행** | **대량 1회성 추출에만** | 워크플로 |
| ⛔ 매 턴 스캔 | 금지 | |
| ⛔ 세션 종료 시 일괄 | 금지 — 세션은 예고 없이 끊긴다 | |

### 6.6 실패 telemetry

- 유저 정정이 발생하면 **어느 층(I/A)의 어떤 실패인지 분류해 기록**한다.
- 목적은 패턴 추출이며, 반복 유형에 구조적 처방을 붙이기 위함이다.
- **구체 사례의 유일한 거처**이며, 스펙 문서에는 사례를 적지 않는다.

### 6.7 세션 부트스트랩

- 새 세션이 **자동으로** 이 문서와 핫셋의 존재를 인지해야 한다.
- 유저의 명시적 지시에 의존하는 부트스트랩은 실패한 설계다.

### 6.8 연결·탐색 층 — 후속 단계

- 사실 기록은 **정합성** 문제를, 링크 그래프는 **탐색·통찰** 문제를 푼다. 둘은 보완재이며 동일하지 않다.
- 도메인을 가로지르는 통찰 생성은 링크 층의 몫이다.
- **외부 노트 도구 호환은 형식 선택으로 거의 무료로 얻는다** — 마크다운 + 위키링크로 기록하면 별도 작업 없이 그래프 탐색이 가능하다. 따라서 §11 D1은 **외부 노트 도구 가독성을 제약으로 포함**한다.
- 후속으로 미루는 이유: 기록이 부정확한 상태에서 링크만 만들면 **틀린 정보가 정교하게 연결된다.** 정합성이 먼저다.

### 6.9 만들지 않는 것 (과잉설계 경계)

| 안 만드는 것 | 이유 | 재검토 조건 |
|---|---|---|
| 오디오 타임스탬프 자동 인덱싱 | 파일 단위 추적으로 충분 | 초 단위 추적이 실제로 필요할 때 |
| 전 문서의 기록화 | 기록은 사실만. 분석은 문서에 남는다 | — |
| 벡터 검색·임베딩 | 현재 규모에서는 전문 검색이 더 빠르고 정확 | 레코드가 수천 건을 넘을 때 |
| 실시간 동기화·매 턴 자동화 | §6.5. 자동화는 오류를 조용히 증폭한다 | — |
| 링크 그래프·외부 도구 연동 | §6.8 | 기록이 안정화된 뒤 |
| 스키마의 조기 일반화 | 한 도메인으로 검증 후 확장 | 두 번째 도메인 적용 시 |

## 7. 상호작용 규범

1. **처방 전에 먼저 묻는다** — 이미 수행된 것, 이미 결정된 것이 있는지.
2. **발화 단계에서 등급을 구분한다** — 사실인지, 전언인지, 추론인지 밝히며 말한다.
3. **정정은 즉시 반영하고 재발을 막는다.**
4. **모르면 모른다고 한다.**
5. **체크리스트를 늘리는 것은 가치가 아니다** — 이미 닫힌 항목을 목록에 넣는 것은 유저의 주의를 낭비하고 문서 신뢰도를 깎는다.

---

## 8. 운영 제약

- **롤백 가능성** — 구조 재구성 전에 되돌릴 수 있는 상태를 만든다. 미커밋 파일이 다수 존재할 수 있음을 전제한다.
- **취급 등급 상속** — 프로젝트 지시가 정한 비공개·동결·인용 제한 규칙을 기록도 그대로 따른다.
- **버전 관리 규율** — 커밋·푸시는 유저의 권한이다. 에이전트는 파일 작성까지 한다.

## 9. 설계 규율

- **과잉설계 경계.** 만들지 않기로 한 것과 그 이유를 명시한다(§6.9).
- 결정 지점마다 **대안 2~3개의 pros/cons를 비교**한 뒤 결정하고, 결정과 근거를 §11·§12에 남긴다.
- 확장성 · 정합성 · 관리 용이성을 종합 고려한다.
- 적당히 타협하지 않는다.

---

## 10. 검증

1. **동작 검증** — 도구가 실제로 동작하는가.
2. **신선 세션 검증** — 새 세션에서 §3의 1~4를 통과하는가. **필수.**
3. **함정 검증** — 기록에 **없는** 것을 물었을 때 "모른다"가 나오는가. 지어내면 실패.
4. **회귀 검증** — 기록이 기존 문서와 모순되지 않는가.
5. **부하 검증** — 일상 대화에 체감 지연이 없는가.

§10-2가 통과하는 시점에 §12에서 `v1.0`을 부여한다.
